# `audit/leads/` —— 多目标文献线索卡（**人工维护，与认领快照无关**）

一篇文献常同时给出多个库内源的测光数据（GRB 样本汇编、TDE/SN 统计文章等）。
审 A 源时顺手读到的 B 源数据，不该随 PR 一起丢掉，也不该让人重读一遍原文。
**线索卡就是把这部分已到手的信息交给下一位审核员的载体。**

## 它是什么 / 不是什么（判据只有这一条）

| 是 | 不是 |
|---|---|
| 别人审另一篇文献时留给你的**待核对清单** | 认领（有卡≠有人在做） |
| 出处、表号、原文口径、已提取的原始行 | 已核验的数据（不能直接抄进 `lc/`） |
| 只读文件，`audit_queue.py` 只展示不参与状态机 | `reviewed` 标记（永不写 `extra_data.audit`） |

**源的 `free / claimed / in-review / reviewed` 判定完全不受线索卡影响**：
状态机只读 `info/*.json` 的 `extra_data.audit` 与改动了 `info/<id>`、`lc/<id>` 的 open PR。
线索卡两者都不碰——所以「有线索卡」的源仍然是 `free`，必须有人独立认领、独立核验。

## 谁写、何时写、何时删

- **写**：审核某个源时，发现同一文献还给出了**库内另一个已存在源**的数据或关键口径（T0/历元、定标、消光）。
  每个其他源写一张卡，**随你被审源的那个数据 PR 一起提交**（《数据审核提示词》§3.11、§7 的范围例外）。
- **不写**：目标源不在库内 → 不建卡，改开 `new-source: <名称>（来自 <DOI> 的多目标线索）` Issue。
- **删**：接手该源的审核员在**自己的数据 PR 里** `git rm audit/leads/<源ID>.md`，并在 PR 说明写清
  采纳了什么、否证了什么。`validate.py` 会对「源已 `reviewed` 但卡还在」发警告。

## 命名与元数据

文件名 **必须**等于源 ID（与 `info/<源ID>.json` 同名）：`audit/leads/GRB130427A.md`。
一源一卡；同一文献涉及 N 个源就写 N 张卡（不要合并成一个文件，避免并行审核时互相覆盖）。

文件开头是元数据区，**遇到第一个 `##` 标题即结束**。键名固定，值单行：

| 键 | 必填 | 含义 |
|---|---|---|
| `source_id` | ✅ | 目标源 ID，须与文件名一致 |
| `status` | ✅ | `extracted`＝已完整提取该源的行；`mention-only`＝只是看到、未提取 |
| `paper` | ✅ | 出处：作者+年份、期刊/卷/页或 arXiv 号、**具体表号** |
| `pr` | ✅ | 提出者当时的 PR 号（`#123`） |
| `helper` | ✅ | 提出者（`人名@代理`） |
| `date` | ✅ | 提出日期 `YYYY-MM-DD` |

## 模板

```markdown
# 线索：GRB 130427A

- source_id: GRB130427A
- status: extracted
- paper: Smith+2024, ApJ 123, 456（DOI 10.3847/0004-637X/123/4/456）表 3
- pr: #123
- helper: zhang@claude-code
- date: 2026-10-18

## 版本状态

VoR 已获取（出版社 PDF）；补充材料 `table3_mrt.txt` 已下载并核对（37 行）。

## 原文口径（原样记录，**未做任何换算**）

- T0 / 历元：2013-04-27 12:00:00 UTC（与 GRB 130427B 同一历元）
- 波段：R、g'；单位：mag（原文声明 AB）；未做银消改正

## 已核对 / 未核对

- 已核对：表号、行数、列名与原文一致；行值逐行对照 PDF 表 3
- 未核对：未去重、未换算到本库 T0、未查其他文献、未判断星等系统是否需改写

## 原始行（原样）

| time | time_unit | band | mag | mag_err | telescope |
|---|---|---|---|---|---|
| 3600 | s | R | 18.42 | 0.05 | LCO 1m |
| ... | | | | | |

## 备注

同一文献还涉及 GRB 130427C（另见 `leads/GRB130427C.md`）。
```

`status: mention-only` 时省略「原始行」一节，其余照填；不得把只看到图/只看到摘要的内容写成 `extracted`。

## 硬性禁令

- 不得修改目标源的 `info/<id>.json` / `lc/<id>.csv`，不得为它写 `extra_data.audit`。
- 不得把目标源 ID 写进 PR **标题**（`gh pr list --search "in:title <源ID>"` 会把它当成认领，
  误占他人的工作入口）；只在 PR 正文和线索卡里提。
- 若原数据 PR 已合并、必须单独补卡，PR 标题**不得含任何已知源 ID**（用 `docs: 补充多目标文献线索卡`
  之类），否则 `audit_queue.py` 在「无 info/lc 改动」时会退化为按标题识别，仍会把目标源误占。
- 不得在卡里做单位换算、T0 换算、消光改正、去重判断——那些属于接手者的审核动作。
- 不得从图上读数；只有图没有表时只能转述图注文字。

## 工具如何消费

```bash
python3 tools/audit_queue.py --leads          # 列出全部线索卡（含源当前状态）
python3 tools/audit_queue.py --id <源ID>      # 该源有卡时直接打印摘要与「必读」提示
python3 tools/audit_queue.py --limit 20       # 队列行尾 +lead(<status>) 标记
python3 tools/validate.py                     # 命名/status/目标源/已审核残留的一致性警告
```

离线可用：卡在仓库文件里，`git pull` 就有，不依赖 `gh` 或 Issue 检索。

## 冲突处理

同一源被两人同时留卡 → 后合并者把两份内容合并进同一文件（按日期倒序并列两节），不要覆盖。
`validate.py` 会提示「一源多卡」。
